1Introduction ¶

Goal: Replace per-record Python decoding with a parallel Go daemon that mmaps files, builds an index, and answers queries via a binary stdio protocol — while preserving the existing Python API.

The Problem

The existing pyHSPF reader (hbn.py) loads each .hbn file into a numpy byte array via np.fromfile, then sequentially walks records, decoding floats with Python-level loops. For typical HSPF output spanning multiple files and many reaches, three bottlenecks dominate:

  1. Whole-file load: 500 MB allocated upfront even if you only query 3 reaches.
  2. Sequential file walk: Files are processed one at a time, no parallelism.
  3. Per-record Python overhead: Each record triggers a Python-level struct.unpack + a slice + a copy.

The Solution: Two Tracks

Track A — Python Quick Wins

Five surgical changes to hbn.py. Total effort: ~1 day. Expected speedup: 5–15× on real workloads.

No subprocess complexity, no new language, ship today.

Track B — Go Daemon

Persistent subprocess, parallel mmap+goroutines. Total effort: ~11 days. Expected speedup: 20–50×.

Drop-in API, but requires a compiled binary alongside the Python package.

Recommended path: do both, in order. Land the Python wins first (they correct a real bug in the back-pointer skip logic), then build the Go daemon from a known-correct baseline.

Why Grounding in Fortran Matters

The HSPF binary format is not formally documented. Every byte-level decision in the parser must match what the Fortran writer actually does, on a specific compiler, with specific compiler-extension semantics. The attached source files — HBINUX.FOR, HBINLH.FOR, HFILES.FOR, and the module callers — are the ground truth. This document derives every parser rule from a specific line of Fortran, with citations.

2The Fortran Foundation ¶

2.1 How the File Gets Opened

Before we can parse a single byte, we need to know what kind of file we're dealing with. The opening logic in HFILES.FOR is decisive: 

! HFILES.FOR — binary output file open path (FILBLK)
IF (FTYPE(I) .EQ. 'BINO ') THEN
  ...
  ACC=  'SEQUENTIAL'
  FRM=  BINFRM           ! "FORMATTED" (from HBINUX.FOR's BINIT)
  RCL = 0
  STAT= 'UNKNOWN'
  CALL FILOPN (ACC, FRM, RCL, STAT, FUNIT(I), FILNAM, RET)
  IF (RET.EQ.0) THEN
    ENDFILE (FUNIT(I))   ! truncate any existing content
    CLOSE (FUNIT(I))
    CALL FILOPN (ACC, FRM, RCL, STAT, FUNIT(I), FILNAM, RET)
  END IF
END IF

The file is opened SEQUENTIAL / FORMATTED. Counterintuitively, this does not mean the file contains text. It means the writer uses Fortran formatted I/O semantics. The trick is in the format string used for every WRITE call: 

! HBINUX.FOR — every record is written this way
WRITE (RECFMT,*) "(",CPOS,"A1,$)"
WRITE (BINU,RECFMT) (BINBUF(I),I=1,CPOS)
🔍 The $ Edit Descriptor

The $ at the end of the format is a non-standard but widely-honored extension (Lahey, Watcom, Salford, gfortran) that suppresses the trailing newline. Combined with A1 single-character output, this means the runtime writes exactly CPOS bytes from BINBUF with zero record terminators inserted.

✅ Implication for our parser

Every byte in the file came from BINBUF. There are no compiler-inserted CR/LF, no record markers, no padding. The file is a flat byte stream we can mmap and address directly. The Python parser's flat-byte-stream assumption is correct.

2.2 Anatomy of a Record

Every record — names or data — has the same outer envelope, built byte-by-byte in BINBUF and then written verbatim:

Figure 1: HSPF binary record structure. The same envelope wraps both names (rectype 0) and data (rectype 1) records.

2.3 The Length Field & Bit Arithmetic

The 4-byte RECLEN at the start of each record uses a packed encoding from PAKLEN: 

! HBINUX.FOR — PAKLEN
! first multiply by 4 to shift left by 2 bits
! then add 3 to specify 3 more bytes
FIELD = LEN * 4 + 3
PI(1) = MOD(FIELD, 256)
PI(2) = INT(FIELD / 256.0)
PI(3) = INT(FIELD / 256.0**2.0)
PI(4) = INT(FIELD / 256.0**3.0)
BINBUF(1) = PC(1)   ! byte 0
BINBUF(2) = PC(5)   ! byte 1
BINBUF(3) = PC(9)   ! byte 2
BINBUF(4) = PC(13)  ! byte 3
Figure 2: The packed length field. Multiply-by-4 + add-3 = shift-left-2 + set-low-2-bits.

2.4 Names vs Data Records

Names record (rectype = 0)

Written by BINHED. Written once per (op, id, activity) at the start of the file.

IBUF(2) = 0           ! rectype
IBUF(3..4) = OPTYP    ! 8 bytes
IBUF(5)   = OPNO      ! 4 bytes
IBUF(6..7) = SECT     ! 8 bytes
! payload: [4-byte len][N bytes name]…

Leader = 20 bytes (no unit/lev/date).

Data record (rectype = 1)

Written by BINREC. Repeated for every printout interval.

IBUF(2) = 1           ! rectype
IBUF(3..4) = OPTYP
IBUF(5)   = OPNO
IBUF(6..7) = SECT
IBUF(8)   = UNITFG
IBUF(9)   = LEV
IBUF(10..14) = DATE   ! year,mo,dy,hr,mn
! payload: float32 × VCOUNT

Leader = 32 bytes. Note RPOS=14 ints × 4 = 56 bytes before floats.

2.5 The Back-Pointer Width Rule

The back-pointer at the end of each record is the trickiest part. PAKLEN writes one, two, or three bytes depending on the total record size: 

! HBINUX.FOR — PAKLEN, after writing payload
FIELD = CPOS * 4 + 1                  ! CPOS = RECLEN + 4 (incl. length prefix)
IF (FIELD .GE. 256**2.0) THEN
  ! three-byte back-pointer
  CPOS = CPOS + 3
ELSE IF (FIELD .GE. 256) THEN
  ! two-byte back-pointer
  CPOS = CPOS + 2
ELSE
  ! one-byte back-pointer
  CPOS = CPOS + 1
END IF

Translating into the variable convention used in hbn.py (where reclen is what comes out of bit-shifting the length prefix and represents the leader+payload only):

Buffer total (CPOS)FIELD = CPOS·4 + 1Back-pointer widthSkip after data (Python reclen)
< 64< 2571 bytereclen + 28 + 1
64 – 16383257 – 655352 bytesreclen + 28 + 2
≥ 16384≥ 655373 bytesreclen + 28 + 3
🐞 Existing Python Bug

hbn.py currently uses the heuristic if reclen < 36: +29 else: +30. This catches the 1-byte and 2-byte cases but silently breaks on 3-byte back-pointers. With MXBBUF=10000 bounding records to ≤ 40,000 payload bytes, this case absolutely occurs in real files for wide RCHRES sections (NUTRX, PLANK with many constituents). The mis-skip cascades — every subsequent record is read from the wrong offset.

3Critical Findings from Source Review ¶

3.1 The Complete OPTYP × Activity Surface

Reviewing every BINHED caller across HSPF125/ reveals the full set of valid (operation, activity) pairs. This is finite and small — it can be modeled as a typed enum in Go:

PERLND

  • ATEMP, SNOW, PWATER, SEDMNT
  • PSTEMP, PWTGAS, PQUAL
  • MSTLAY, PEST, NITR
  • PHOS, TRACER

IMPLND

  • ATEMP, SNOW
  • IWATER, SOLIDS
  • IWTGAS, IQUAL

RCHRES

  • HYDR, CONS, HTRCH, SEDTRN, GQUAL, OXRX, NUTRX, PLANK, PHCARB, ACIDPH
  • Note: ADCALC has no printout fluxes (per HRCH.FOR) — never appears in files.

3.2 The Hyphenated Constituent Name Issue

For multi-exit reaches, HRCHOXR.FOR shows how distinguishing names are constructed:

! HRCHOXR.FOR — multi-exit constituent naming
IF (NEXITS .GT. 1) THEN
  DO 60 I= 1, NEXITS
    CALL INTCHR (I, I2, I1, JLEN, CSTR)
    ACNT = ACNT + 1
    CHEAD(ACNT) = 'BODOUT-EXIT'
    DO 50 IX= 1, JLEN
      CHEAD(ACNT) = TRIM(CHEAD(ACNT)) // CSTR(IX)
50  CONTINUE
    CLEN(ACNT) = LEN_TRIM(CHEAD(ACNT))   ! ← name is already trimmed
60 CONTINUE
END IF

This produces real names like BODOUT-EXIT1, BODOUT-EXIT2. The current Python parser does:

names.append(name.replace('-', ''))  # → "BODOUTEXIT1", "BODOUTEXIT2"
⚠️ Information loss

The dash-stripping is information-destroying. It works as long as everything downstream is consistent, but hides legitimate distinctions and could hypothetically collide names from different HSPF versions. Recommendation: keep both the raw (with dash) and normalized (without) forms — store raw as the public column name, match queries against normalized.

3.3 Names Are Already Trimmed

CLEN(ACNT) = LEN_TRIM(CHEAD(ACNT)) means the writer stores only meaningful bytes — no trailing spaces. The Python parser's .strip() on names is redundant. In Go, we skip it entirely.

3.4 Names Have Zero Padding

HBINUX.FOR shows the names are written by CVARAR(CLEN(I), CHEAD(I), CLEN(I), …) — the third argument equals the first, so no padding/truncation logic engages. Names in the file are exactly CLEN bytes, byte-aligned, no zero-termination, no length-rounding. The parser must use the exact byte count, never round up.

3.5 Float Offset Within Data Records

In BINREC, RPOS = 14 in integer indices, so 14 × 4 = 56 bytes precede the float values: 4 bytes length-prefix + 4 rectype + 8 optyp + 4 opno + 8 sect + 4 unitfg + 4 lev + 20 date = 56 bytes. Float data starts at recordStart + 56.

3.6 Every File Starts with 0xFD

First call to BINHED writes the magic byte: 

IF (FDFLAG(BINU) .EQ. 0) THEN
  IBUF(1) = 253           ! 0xFD
  WRITE (BINU,"(A1,$)") BINBUF(1)
  FDFLAG(BINU) = 1
END IF

The parser must skip byte 0 before walking records.

4.1 mmap Replaces np.fromfile

📦 Quick Win #1: Memory Mapping

~5 lines ~30% faster startup Low risk

The problem

# Current code in hbn.py __init__:
self.data = np.fromfile(file, 'B')

For a 500MB .hbn file, this allocates ~500 MB of RAM and reads every byte from disk — even if your query touches three reaches in one corner of the file.

Figure 3: mmap dramatically reduces RAM and startup time when only part of the file is queried.

The fix

import mmap

class hbnClass:
    def __init__(self, file):
        self.file = file
        with open(file, 'rb') as fh:
            # Map entire file. ACCESS_READ = read-only, won't be modified.
            self._mmap = mmap.mmap(fh.fileno(), 0, access=mmap.ACCESS_READ)
        # numpy "views" the mmap region — no allocation, no copy
        self.data = np.frombuffer(self._mmap, dtype='B')
        # ... rest of __init__ unchanged ...
        self.map_hbn()

    def __del__(self):
        # Release the mapping when the object is garbage collected
        if hasattr(self, '_mmap'):
            self._mmap.close()

Why it works

  • np.frombuffer creates a numpy array that views the bytes in the mmap region. No allocation, no copy.
  • All existing code patterns (self.data[i:i+4].view('I')[0], slicing, etc.) work without modification.
  • The OS pages in only the bytes you actually touch — typical 4KB granularity.
  • Startup goes from "read 500MB from disk" to "open a file descriptor and create a mapping" — essentially instant.

4.2 Back-Pointer Skip Fix

🐞 Quick Win #2: Back-Pointer Bug Fix

~5 lines Correctness No risk — bug fix

The problem

# Current code in map_hbn:
if reclen < 36:
    index += reclen + 29
else:
    index += reclen + 30

This handles the 1-byte and 2-byte back-pointer cases but completely misses the 3-byte case. When the writer emits a wide record (CPOS·4 + 1 ≥ 65,537, i.e., CPOS ≥ 16,384, which means a record with payload around 16 KB or larger — common for RCHRES sections with many constituents), the parser silently mis-skips by 1 byte and corrupts every subsequent record's offset.

The fix

# In map_hbn, replace the skip logic with:
cpos = reclen + 28  # 28 = 4-byte length prefix + 24-byte leader

if cpos < 64:
    bp_width = 1
elif cpos < 16384:
    bp_width = 2
else:
    bp_width = 3

index += reclen + 28 + bp_width
Figure 4: Back-pointer width zones. The 3-byte zone is real and untested by the existing parser.

Verifying the fix in practice

Add this to a test fixture: write an HBN file with a single RCHRES NUTRX names record containing 30+ constituents. The total names record will exceed 16 KB. Parse it with both the old and new logic; the old code will produce a wrong offset for record #2.

4.3 Pre-Built Activity Lookup Table

⚡ Quick Win #3: O(1) Activity Inference

~10 lines ~10× on infer_activity Low risk

The problem

infer_activity() currently does a linear scan of self.mapn on every call. For a 50-reach query, that's 50 scans of an O(headers × constituents) structure.

Figure 5: Algorithmic improvement from O(N·M) per call to O(1) per call.

The fix

def map_hbn(self):
    # ... existing scanning code ...

    # NEW: at the end, build the lookup table once.
    # Store both raw and dash-stripped variants so users can
    # query with or without dashes (preserves backward compat).
    self._cons_to_activity = {}
    for (op, oid, activity, tcode), names in self.mapn.items():
        for name in names:
            self._cons_to_activity[(op, name)] = activity
            stripped = name.replace('-', '')
            if stripped != name:
                self._cons_to_activity[(op, stripped)] = activity

def infer_activity(self, op, constituent):
    return self._cons_to_activity.get((op, constituent))

Bonus: preserves the dash-name fix

By indexing by both "BODOUT-EXIT1" and "BODOUTEXIT1", you can now expose the raw hyphenated names as DataFrame columns without breaking any existing caller that's been passing the stripped form.

4.4 Cache read_data Results

💾 Quick Win #4: Result Cache

~20 lines 5–50× on repeat queries Low risk

The problem

Calibration loops, sensitivity analyses, and interactive notebook workflows all routinely re-request the same time series. read_data currently re-reads from disk and rebuilds the DataFrame every time.

The fix

class hbnClass:
    def __init__(self, file):
        # ... existing code ...
        self._cache = {}  # (op, id, activity, tcode) → DataFrame

    def read_data(self, op, oid, activity, tcode):
        key = (op, oid, activity, tcode)
        if key in self._cache:
            return self._cache[key]

        # ... existing read_data body produces df ...

        self._cache[key] = df
        return df

    def clear_cache(self):
        """Drop cached frames to free memory."""
        self._cache.clear()
💡 Memory hint

The cache grows monotonically. For long-running notebook sessions querying many distinct keys, expose clear_cache() so users can manage memory. For typical batch workflows the cache fits comfortably in RAM (each time series is N × num_constituents × 4 bytes).

4.5 ThreadPoolExecutor for Multi-Reach Queries

🧵 Quick Win #5: Concurrent Multi-Reach Reads

~30 lines 3–5× on multi-reach Medium risk

The problem

get_multiple_timeseries walks opnids sequentially. Each iteration involves file I/O (mmap page-faults, after Quick Win #1) and numpy slicing — both of which release the GIL. Threading them yields linear speedup up to ~core-count.

Figure 6: Concurrent reach reads. Speedup is ~core-count up to disk-I/O saturation.

The fix

from concurrent.futures import ThreadPoolExecutor

def get_multiple_timeseries(self, t_opn, t_code, t_con, opnids=None):
    if isinstance(t_code, str):
        t_code = self.tcodes[t_code]
    if opnids is None:
        opnids = self.infer_opnids(t_opn, t_con)

    activity = self.infer_activity(t_opn, t_con)  # O(1) after Quick Win #3

    def fetch_one(oid):
        for hbn in self.hbns:
            key = (t_opn, oid, activity, t_code)
            if key in hbn.mapd:
                return oid, hbn.read_data(t_opn, oid, activity, t_code)[t_con]
        return oid, None

    # Threshold: avoid pool overhead for tiny queries
    if len(opnids) < 8:
        results = dict(fetch_one(oid) for oid in opnids)
    else:
        max_workers = min(8, len(opnids))
        with ThreadPoolExecutor(max_workers=max_workers) as ex:
            results = dict(ex.map(fetch_one, opnids))

    return pd.DataFrame({oid: s for oid, s in results.items() if s is not None})
⚠️ Cache contention

If you've already added Quick Win #4 (caching), wrap reads/writes to self._cache in a threading.Lock, or use threading.RLock for safety. Otherwise concurrent inserts can corrupt the dict.

5Go Daemon Architecture ¶

The Big Picture

The Go implementation is a persistent daemon — Python launches it once at the start of a session and exchanges binary messages with it over stdin/stdout. The daemon owns all file handles, the index, and the cache.

Figure 7: Component layout. Python sees a normal hbnInterface; behind the scenes everything is delegated to a Go subprocess.

Why a Persistent Daemon (Not Per-Query Subprocess)

❌ Per-query subprocess

  • Each query: spawn process (~50ms)
  • Each query: re-index every file (~seconds for large files)
  • Cache discarded after every query
  • 50 queries × 50ms startup = 2.5s pure overhead

✅ Persistent daemon

  • Spawned once at session start
  • Index built once, reused for all queries
  • Cache lives across queries
  • 50 queries × <1ms each

6Go Concepts Primer ¶

If you're coming from Python, four concepts underpin everything in this plan.

6.1 Goroutines

A goroutine is a lightweight concurrent task — think of it as a thread without the OS overhead. Unlike Python threads, goroutines run truly in parallel because Go has no GIL.

Figure 8: Goroutines run truly in parallel. The go keyword launches one.
// Sequential
for _, file := range files {
    processFile(file)  // each blocks the next
}

// Parallel
for _, file := range files {
    go processFile(file)  // each runs independently
}

6.2 Channels

A channel is a typed pipe between goroutines. One sends, the other receives. This is how parallel goroutines safely return results to a caller.

results := make(chan Result, len(files))

for _, file := range files {
    go func(f string) {
        results <- processFile(f)  // send result into channel
    }(file)
}

// Collect all results
for i := 0; i < len(files); i++ {
    r := <-results  // receive (blocks until one arrives)
    fmt.Println(r)
}

6.3 Memory Mapping (mmap)

Tell the OS "map this file into my address space" — pages load on first access via page-fault. Same idea as Python Quick Win #1, but with sub-millisecond access.

6.4 The Buffer Pool (sync.Pool)

Reading binary data needs byte buffers. Allocating one per record creates millions of short-lived allocations that pressure the garbage collector. A pool keeps a small set of reusable buffers.

Figure 9: sync.Pool eliminates allocation pressure on the hot path.

Types & Definitions

PHASE 1
File: hbn/types.go Effort: 0.5 day Dependencies: None

Goal

Define every shared data type used across the codebase. No logic — just definitions.

Why It Comes First

Every other module depends on agreement about what a "record key" is. Defining them first prevents painful refactors later.

Core Types

package hbn

// RecordKey uniquely identifies any time series in any HBN file.
// This is the Go equivalent of the Python tuple (op, id, activity, tcode).
type RecordKey struct {
    Operation Operation  // typed enum: PERLND / IMPLND / RCHRES
    ID        int32      // segment number
    Activity  Activity   // typed enum: HYDR, PWATER, SEDMNT, ...
    TCode     int8       // 1=min, 2=hourly, 3=daily, 4=monthly, 5=annual
}

// Constituent stores both raw and normalized forms of a name.
// Raw preserves "BODOUT-EXIT1" for display; Normalized is the lookup key.
type Constituent struct {
    Raw        string
    Normalized string  // raw with hyphens stripped, uppercase
}

// LocalRecordRef is a (offset, length) pair within ONE file.
type LocalRecordRef struct {
    Offset int64
    Length int32
}

// GlobalRecordRef adds a file index for cross-file scatter patterns.
type GlobalRecordRef struct {
    FileIndex int8
    Offset    int64
    Length    int32
}

// LocalFileIndex is what a single goroutine produces while scanning one file.
type LocalFileIndex struct {
    MapN map[RecordKey][]Constituent       // names records
    MapD map[RecordKey][]LocalRecordRef    // data record offsets
}

// GlobalIndex is the merged result across all files.
type GlobalIndex struct {
    MapN map[RecordKey][]Constituent
    MapD map[RecordKey][]GlobalRecordRef
}

// TimeSeriesRecord is the final parsed payload returned to Python.
type TimeSeriesRecord struct {
    Key        RecordKey
    Names      []string    // raw names (with hyphens)
    Timestamps []int64     // unix seconds
    Values     [][]float32 // [timestep][constituent], row-major
}

Single-File Index Builder

PHASE 2
File: hbn/mapper.go Effort: 2 days Dependencies: Phase 1

Goal

Scan one HBN file's records start-to-finish, reading only the header bytes of each record, and build a LocalFileIndex. Direct translation of map_hbn().

Why It Exists

This is the heart of the lazy strategy. Reading only 28-byte headers during the scan tells us where every record starts — without loading any float data. Floats are read later, on demand, in Phase 4.

Algorithm

Figure 10: Single-file scanner flowchart. Names records read fully (so we can extract constituent names); data records skip the float payload entirely.
package hbn

import (
    "encoding/binary"
    "io"
    "strings"
)

func ScanFileHeaders(r io.ReaderAt, fileSize int64) (*LocalFileIndex, error) {
    idx := &LocalFileIndex{
        MapN: make(map[RecordKey][]Constituent),
        MapD: make(map[RecordKey][]LocalRecordRef),
    }

    offset := int64(1) // skip 0xFD magic byte
    headerBuf := make([]byte, 32)

    for offset < fileSize {
        // Read 28-byte fixed leader (length + rectype + optyp + opno + sect)
        if _, err := r.ReadAt(headerBuf[:28], offset); err != nil {
            if err == io.EOF { break }
            return nil, err
        }

        // Decode packed length: drop low 2 bits
        field := binary.LittleEndian.Uint32(headerBuf[0:4])
        reclen := int32(field >> 2)

        rectype := binary.LittleEndian.Uint32(headerBuf[4:8])
        optyp   := strings.TrimSpace(string(headerBuf[8:16]))
        opno    := int32(binary.LittleEndian.Uint32(headerBuf[16:20]))
        sect    := strings.TrimSpace(string(headerBuf[20:28]))

        op,  _ := ParseOperation(optyp)
        act, _ := ParseActivity(sect)

        switch rectype {
        case 0: // names record
            // Read full payload
            body := make([]byte, reclen-20)  // 20 = leader bytes counted in reclen
            r.ReadAt(body, offset+28)
            names := parseNames(body)
            key := RecordKey{Operation: op, ID: opno, Activity: act, TCode: 0}
            idx.MapN[key] = names

        case 1: // data record — only need tcode
            tcodeBytes := headerBuf[28:32]
            r.ReadAt(tcodeBytes, offset+28)
            // Note: writer puts UNITFG at 28..32, LEV at 32..36; tcode is LEV
            tcode := int8(binary.LittleEndian.Uint32(headerBuf[32:36]))
            key := RecordKey{Operation: op, ID: opno, Activity: act, TCode: tcode}
            idx.MapD[key] = append(idx.MapD[key], LocalRecordRef{
                Offset: offset, Length: reclen,
            })
        }

        // Advance: 28 = length+leader, plus bp_width per Phase 2 fix
        cpos := reclen + 28
        var bpWidth int32
        switch {
        case cpos < 64:    bpWidth = 1
        case cpos < 16384: bpWidth = 2
        default:           bpWidth = 3
        }
        offset += int64(28 + reclen + bpWidth)
    }

    return idx, nil
}

// parseNames decodes the variable-length name list in a names record body.
func parseNames(body []byte) []Constituent {
    var names []Constituent
    pos := 0
    for pos < len(body) {
        ln := int(binary.LittleEndian.Uint32(body[pos : pos+4]))
        pos += 4
        raw := string(body[pos : pos+ln])
        // Note: writer already trimmed via LEN_TRIM (HRCHOXR.FOR §3.3),
        // so no .Trim() needed.
        names = append(names, Constituent{
            Raw:        raw,
            Normalized: strings.ToUpper(strings.ReplaceAll(raw, "-", "")),
        })
        pos += ln
    }
    return names
}
⚠️ Compile-time safety check

Add a defensive sniff after mapping the file: scan the first 8 KB for stray '\n' outside name regions. If found, fail fast with "this HBN was written by a non-$-honoring compiler". This is one CPU instruction per file open and saves enormous debugging time.

Multi-File Parallel Server

PHASE 3
File: hbn/server.go Effort: 1 day Dependencies: Phases 1, 2

Goal

Launch one goroutine per HBN file, collect results, merge into a GlobalIndex. Owns mmap handles and the cache.

The Parallel Build

Figure 11: All files indexed concurrently. Total wall-clock ≈ time for the slowest single file.
package hbn

import (
    "os"
    "sync"
    "syscall"
)

type HBNServer struct {
    readers     []*MmapReader
    globalIndex *GlobalIndex

    cache    map[RecordKey]*TimeSeriesRecord
    cacheMu  sync.RWMutex

    bufferPool sync.Pool

    // Pre-built lookup: (operation, normalized constituent) → activity
    activityLookup map[constituentKey]Activity
}

type constituentKey struct {
    Op  Operation
    Con string
}

type indexResult struct {
    fileIndex int8
    local     *LocalFileIndex
    err       error
}

func NewHBNServer(filepaths []string) (*HBNServer, error) {
    n := len(filepaths)
    srv := &HBNServer{
        readers: make([]*MmapReader, n),
        globalIndex: &GlobalIndex{
            MapN: make(map[RecordKey][]Constituent),
            MapD: make(map[RecordKey][]GlobalRecordRef),
        },
        cache: make(map[RecordKey]*TimeSeriesRecord),
        bufferPool: sync.Pool{
            New: func() interface{} { b := make([]byte, 64*1024); return &b },
        },
    }

    // 1. Open all files (sequential — file open is fast)
    for i, fp := range filepaths {
        rd, err := OpenMmap(fp)
        if err != nil { return nil, err }
        srv.readers[i] = rd
    }

    // 2. Launch one goroutine per file
    results := make(chan indexResult, n)
    for i, rd := range srv.readers {
        go func(idx int8, r *MmapReader) {
            local, err := ScanFileHeaders(r, r.Size())
            results <- indexResult{fileIndex: idx, local: local, err: err}
        }(int8(i), rd)
    }

    // 3. Collect and merge
    var mergeMu sync.Mutex
    for i := 0; i < n; i++ {
        res := <-results
        if res.err != nil { return nil, res.err }
        mergeMu.Lock()
        srv.merge(res.fileIndex, res.local)
        mergeMu.Unlock()
    }

    // 4. Build the constituent → activity lookup
    srv.buildActivityLookup()
    return srv, nil
}

func (srv *HBNServer) merge(fileIdx int8, local *LocalFileIndex) {
    for key, names := range local.MapN {
        if _, ok := srv.globalIndex.MapN[key]; !ok {
            srv.globalIndex.MapN[key] = names
        }
    }
    for key, refs := range local.MapD {
        for _, r := range refs {
            srv.globalIndex.MapD[key] = append(srv.globalIndex.MapD[key],
                GlobalRecordRef{FileIndex: fileIdx, Offset: r.Offset, Length: r.Length})
        }
    }
}

func (srv *HBNServer) buildActivityLookup() {
    srv.activityLookup = make(map[constituentKey]Activity)
    for key, cons := range srv.globalIndex.MapN {
        for _, c := range cons {
            srv.activityLookup[constituentKey{key.Operation, c.Normalized}] = key.Activity
        }
    }
}

On-Demand Data Reader

PHASE 4
File: hbn/reader.go Effort: 1.5 days Dependencies: Phases 1–3

Goal

Given a RecordKey, use the offsets in GlobalIndex.MapD to read only the float data for that key, in parallel across files.

The Scatter Pattern

In real HSPF runs, one reach's data may be split across multiple files (different runs concatenated, or a single run that spilled). The reader handles this transparently:

Figure 12: Scatter-pattern read. Per-file goroutines run in parallel; results merge-sorted by timestamp.
// ReadConstituent fetches all data for a key, in parallel across files.
func (srv *HBNServer) ReadConstituent(key RecordKey) (*TimeSeriesRecord, error) {
    // 1. Cache check
    srv.cacheMu.RLock()
    if rec, ok := srv.cache[key]; ok {
        srv.cacheMu.RUnlock()
        return rec, nil
    }
    srv.cacheMu.RUnlock()

    // 2. Find offsets, group by file
    refs, ok := srv.globalIndex.MapD[key]
    if !ok { return nil, fmt.Errorf("key not found: %v", key) }

    byFile := map[int8][]GlobalRecordRef{}
    for _, r := range refs {
        byFile[r.FileIndex] = append(byFile[r.FileIndex], r)
    }

    // 3. Parallel reads
    type chunk struct {
        timestamps []int64
        values     [][]float32
    }
    chunks := make(chan chunk, len(byFile))

    for fileIdx, fileRefs := range byFile {
        go func(idx int8, refs []GlobalRecordRef) {
            bufPtr := srv.bufferPool.Get().(*[]byte)
            defer srv.bufferPool.Put(bufPtr)

            ts, vals := readRecords(srv.readers[idx], refs, bufPtr)
            chunks <- chunk{timestamps: ts, values: vals}
        }(fileIdx, fileRefs)
    }

    // 4. Collect & merge-sort
    var allTs []int64
    var allVals [][]float32
    for i := 0; i < len(byFile); i++ {
        c := <-chunks
        allTs = append(allTs, c.timestamps...)
        allVals = append(allVals, c.values...)
    }
    sortByTimestamp(allTs, allVals)

    // 5. Build record, cache, return
    names := make([]string, len(srv.globalIndex.MapN[key]))
    for i, c := range srv.globalIndex.MapN[key] {
        names[i] = c.Raw
    }
    rec := &TimeSeriesRecord{
        Key: key, Names: names,
        Timestamps: allTs, Values: allVals,
    }
    srv.cacheMu.Lock()
    srv.cache[key] = rec
    srv.cacheMu.Unlock()
    return rec, nil
}
📍 Float offset within record

Per Section 3.5: float data starts at recordStart + 56 (4 bytes length-prefix + 4 rectype + 8 optyp + 4 opno + 8 sect + 4 unitfg + 4 lev + 20 date). The number of floats is (reclen - 32) / 4.

Multi-OPNID Query Handler

PHASE 5
File: hbn/query.go Effort: 1 day Dependencies: Phase 4

Goal

The most common query: "give me constituent X for all reach IDs [1..50] across all files". Direct replacement for Python's get_multiple_timeseries loop.

Two Layers of Parallelism

Figure 13: Each opnid goroutine internally fans out to per-file goroutines (Phase 4), so the runtime spawns up to opnids × files concurrent reads.
func (srv *HBNServer) QueryMultiple(
    op Operation, tcode int8, constituent string, opnids []int32,
) (map[int32]*TimeSeriesRecord, error) {

    // O(1) activity inference (Phase 3 lookup)
    activity := srv.activityLookup[constituentKey{op, normalize(constituent)}]
    if activity == ActUnknown {
        return nil, fmt.Errorf("constituent %q not found for %v", constituent, op)
    }

    type result struct {
        opnid int32
        rec   *TimeSeriesRecord
        err   error
    }

    results := make(chan result, len(opnids))
    for _, oid := range opnids {
        go func(o int32) {
            key := RecordKey{Operation: op, ID: o, Activity: activity, TCode: tcode}
            rec, err := srv.ReadConstituent(key)
            results <- result{opnid: o, rec: rec, err: err}
        }(oid)
    }

    out := make(map[int32]*TimeSeriesRecord, len(opnids))
    for i := 0; i < len(opnids); i++ {
        r := <-results
        if r.err == nil { out[r.opnid] = r.rec }
    }
    return out, nil
}

Binary Wire Protocol

PHASE 6
File: hbn/protocol.go Effort: 1 day Dependencies: Phase 1

Goal

Encode TimeSeriesRecord into compact binary that Python decodes with one np.frombuffer call — no parsing loops.

Why Binary, Not JSON

JSON encoding

For 8,760 hourly floats:

  • [1.234567, 0.987654, ...]
  • ~10 chars per float = ~87,600 bytes
  • Python parses each character into a Python float
  • Per-value object allocation

Binary encoding

For the same 8,760 floats:

  • 4 bytes per float, exactly
  • 35,040 bytes total (2.5× smaller)
  • np.frombuffer reads in one call
  • No per-value parsing — ~50× faster decode

Message Layout

Figure 14: Binary message layout. Each section reads in a single Python call.
// WriteRecord encodes a TimeSeriesRecord and writes it to w.
func WriteRecord(w *bufio.Writer, rec *TimeSeriesRecord) error {
    namesJoined := strings.Join(rec.Names, "\t")
    n := int32(len(rec.Timestamps))
    c := int32(len(rec.Names))
    nb := int32(len(namesJoined))

    w.WriteByte(0x02)              // OK
    binary.Write(w, binary.LittleEndian, n)
    binary.Write(w, binary.LittleEndian, c)
    binary.Write(w, binary.LittleEndian, nb)
    w.WriteString(namesJoined)

    // timestamps as one big int64 block
    binary.Write(w, binary.LittleEndian, rec.Timestamps)

    // values as one big float32 block, row-major
    for _, row := range rec.Values {
        binary.Write(w, binary.LittleEndian, row)
    }
    return nil
}

package main

import (
    "bufio"
    "encoding/json"
    "os"
    "strings"

    "hbn-daemon/hbn"
)

func main() {
    filepaths := os.Args[1:]
    srv, err := hbn.NewHBNServer(filepaths)
    if err != nil {
        os.Stderr.WriteString("init error: " + err.Error() + "\n")
        os.Exit(1)
    }

    // Send ready signal as JSON line
    summary := map[string]int{
        "files":    len(filepaths),
        "headers":  len(srv.GlobalIndex().MapN),
        "data_recs": len(srv.GlobalIndex().MapD),
    }
    json.NewEncoder(os.Stdout).Encode(summary)

    in := bufio.NewReader(os.Stdin)
    out := bufio.NewWriterSize(os.Stdout, 1024*1024) // 1 MB output buffer
    defer out.Flush()

    for {
        line, err := in.ReadString('\n')
        if err != nil { return }
        line = strings.TrimSpace(line)
        parts := strings.Fields(line)
        if len(parts) == 0 { continue }

        switch parts[0] {
        case "read":
            handleRead(srv, out, parts[1:])
        case "multi":
            handleMulti(srv, out, parts[1:])
        case "opnids":
            handleOpnids(srv, out, parts[1:])
        case "clearcache":
            srv.ClearCache()
            out.WriteString(`{"ok":true}` + "\n")
        case "quit":
            return
        }
        out.Flush()
    }
}
📡 Why stdin/stdout instead of a socket?

Pipes are inherited automatically by subprocesses, require no port allocation, and clean up automatically when either side exits. For a single-machine, single-language pairing, they're simpler than any alternative.

Python Wrapper

Goal

import subprocess
import struct
import json
import numpy as np
import pandas as pd

class GoHBNInterface:
    """Drop-in replacement for hbnInterface, backed by Go daemon."""

    def __init__(self, file_paths):
        self.proc = subprocess.Popen(
            ['hbn-daemon'] + list(file_paths),
            stdin=subprocess.PIPE,
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            bufsize=0,
        )
        # First line is the JSON ready signal
        self.summary = json.loads(self.proc.stdout.readline())
        self.tcodes = {'minute': 1, 'hourly': 2, 'daily': 3, 'monthly': 4, 'annual': 5}

    def _send(self, cmd):
        self.proc.stdin.write((cmd + '\n').encode())
        self.proc.stdin.flush()

    def _read_binary_response(self):
        pipe = self.proc.stdout
        header = pipe.read(13)
        msg_type, n, c, nb = struct.unpack('<BIII', header)

        if msg_type == 0x03:  # error
            raise ValueError(pipe.read(nb).decode())

        names = pipe.read(nb).decode().split('\t')
        ts_bytes = pipe.read(n * 8)
        timestamps = np.frombuffer(ts_bytes, dtype=np.int64)
        val_bytes = pipe.read(n * c * 4)
        values = np.frombuffer(val_bytes, dtype=np.float32).reshape(n, c)
        index = pd.to_datetime(timestamps, unit='s')
        return pd.DataFrame(values, index=index, columns=names)

    def get_multiple_timeseries(self, t_opn, t_code, t_con, opnids=None):
        if isinstance(t_code, str):
            t_code = self.tcodes[t_code]

        if opnids is None:
            self._send(f'opnids {t_opn} {t_con}')
            opnids = json.loads(self.proc.stdout.readline())

        opnids_str = ' '.join(str(o) for o in opnids)
        self._send(f'multi {t_opn} {t_code} infer {t_con} {opnids_str}')

        count = struct.unpack('<I', self.proc.stdout.read(4))[0]
        frames = {}
        for _ in range(count):
            opnid = struct.unpack('<I', self.proc.stdout.read(4))[0]
            df = self._read_binary_response()
            frames[opnid] = df[t_con]
        return pd.DataFrame(frames)

    def __del__(self):
        try:
            self._send('quit')
            self.proc.wait(timeout=5)
        except Exception:
            self.proc.kill()

Methods like get_simulated_flow, reach_losses, etc. only call get_multiple_timeseries — they never touch files directly. Inheriting from GoHBNInterface means they Just Work without modification.

⚠️ Float-precision tolerance

The Python parser stores floats as float64 internally even though the file contains float32. The Go pipeline stays float32 end-to-end. Use rtol=1e-5, atol=1e-5 — any tighter and you'll see spurious failures from float32 round-trip.

Recommended Sequence

Do the Python wins first — they correct a real bug (Section 4.2) and establish a known-correct baseline against which Go output can be parity-tested.

Decision Tree

✅ Stop after Track A if…

  • 5–15× speedup is sufficient for your workflow
  • You don't want a Go binary alongside the Python package
  • Distribution complexity (CGo cross-compile, etc.) is a concern
  • You're a small team with no Go experience

SECT / ActivityModule section name. "HYDR ", "PWATER ", etc. See Section 3.1 for full list.
UNITFGUnit system flag. 1 = English, 2 = Metric.
LEV / TCodeOutput time level. 2 = PIVL (sub-daily), 3 = daily, 4 = monthly, 5 = annual.
VCOUNTNumber of constituent values in a data record.
RECLENRecord length (after unpacking). Counts everything from the start of leader through the payload, but not the 4-byte length prefix or the back-pointer.
CPOSInternal cursor in BINBUF. Equals length-prefix + leader + payload before the back-pointer is appended.
FDFLAGPer-unit flag tracking whether the magic 0xFD has been written. Forces it on first call.
PIVLPrint interval. Number of simulation timesteps per output row at level 2.
scatter patternWhen data for one (op, id, activity) key is split across multiple HBN files (typically from concatenated runs).
mmapMemory-mapping. The OS maps a file into your address space; pages load on first access.
goroutineGo's lightweight concurrent task. Cheaper than an OS thread, no GIL.
channelTyped communication pipe between goroutines. chan T for type T.
sync.PoolReusable object pool. Eliminates GC pressure for hot-path allocations.
